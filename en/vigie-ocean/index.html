01

The problem: data under licence

UPPA Tech is the instrumentation service centre of the Université de Pau et des Pays de l'Adour. It is neither an isolated laboratory nor an administrative department: it is a shared platform that puts heavy instrumentation at the disposal of research teams in geosciences, environmental chemistry, marine biology and physics.

That organisation lives with a constraint that shaped everything in my assignment: data sovereignty. Modern oceanographic sensors are sold with a subscription to the manufacturer's proprietary cloud platform. Every brand imposes its own interface, its own file format and its own recurring cost. For a public body running instruments from several vendors, the bill is twofold: scientific data fragments into incompatible silos, and the operating budget is drained by subscriptions whose renewal is never guaranteed.

Vigie Océan was born of the decision to take that chain back. The platform tracks the hydro-physical, biological and spectrometric state of the Basque coast — specifically the Adour estuary and its outflow into the sea off Bayonne.

02

Three tensions to resolve

The thread running through the whole project

IHeterogeneity

Every manufacturer serialises its readings its own way. The Observator box produces files structured by channel, the NKE probe emits a timestamped CSV plus semicolon- separated alarm files, and other gateways follow yet other conventions. Without a normalisation layer, no rigorous comparison between two probes is possible: the quantities share neither the same unit nor the same time reference.

IITime

The probes record in French local time, which shifts twice a year. A reading timestamped "14:00" means nothing until you know whether it is local time or universal time. Data whose timezone is not stated is scientifically ambiguous data.

IIITrust

A submerged probe goes through maintenance, calibration drift, accidental lifts out of the water. These episodes produce outliers that distort interpretation if shown without distinction. But deleting them would irreversibly alter the raw archive — something a scientific instrument cannot afford.

Why it matters These three tensions are not a report outline: they are the constraints that dictated every technical decision that follows — the parser registry, UTC storage, and reversible logical deletion.

04

Seven containers, explicit contracts

The whole infrastructure is described by a single Docker Compose file orchestrating seven containers with clearly separated responsibilities. That property is not cosmetic: it guarantees the platform rebuilds identically, a necessary condition for a project meant to outlive my departure.

Every boundary between two containers is a contract I had to specify: the file format between probes and ingestion, the relational schema between ingestion and the database, the REST contract between the API and the frontend. A large part of the work was making those contracts explicit and stable.

05

Ingestion: never lose a file

The ingestion daemon has a single responsibility: turn a raw file dropped by a probe into normalised rows ready to insert. It watches the drop directory fed by the FTP server using the watchdog library, which relies on kernel notifications and avoids any active polling.

Two field traps

That event-driven responsiveness, elegant on paper, turned out to be insufficient in real conditions. Volumes mounted inside a Docker container do not always faithfully propagate the host's filesystem events: a dropped file could go unnoticed. So I backed the event detection with a periodic safety sweep that walks the directory at a regular interval and catches whatever a missed notification left behind. The redundancy costs little and guarantees the only property that matters for a scientific archive: no deposited data is ever lost.

The second trap is specific to FTP: a file being written is visible long before its transfer completes, and the parser risked reading truncated content. The fix is to watch the file size and only start processing once that size has held steady across several successive observations. A lock materialised by a .processing file also prevents the same reading being handled twice by concurrent runs.

A parser registry, not a naming convention

Rather than forcing a single format on every station, each parser exposes two methods: can_parse inspects the first lines of a file to decide whether it knows how to decode it, and parse produces the list of normalised measurements. A factory queries the parsers in turn and hands the file to the first one that recognises it. This detection by content, rather than by a fragile filename, makes the system robust to naming variations.

Separating electronics from physics

The NKE probe does not only emit measurements: it also reports the state of its electronics. Code D980 means low battery voltage, D981 a position drift beyond the allowed swinging radius, D982 a GPS response timeout, F053 a fault on the chlorophyll a channel. These events are essential for diagnosing the instrument — and have no business on a salinity chart. The alarm parser isolates them into a separate stream, surfaced in the system health tab, while the physical curves stay free of those artefacts.

Time, settled once and for all

At ingestion, every naive timestamp is anchored to the Europe/Paris zone then converted to universal time before insertion.

This corrects an inherited defect: the box previously applied a hard-coded two-hour offset that was only valid during summer time and wrong the rest of the year. By delegating the conversion to the timezone database, which knows the seasonal switching rules, both stations line up on the same scale in every season.

The final insert relies on a composite primary key (time, station_id, parameter). Re-inserting the same measurement — common when a probe retransmits a file — is absorbed without duplication by a conflict resolution clause. That idempotence is what makes replays safe.

06

Storage: a 12.7× factor, losslessly

Vigie Océan's data are regular time series: the same quantities, at the same fifteen-minute step, indefinitely. That profile calls for a specialised engine — TimescaleDB, an extension of PostgreSQL 16, which keeps all the richness of relational SQL while adding time-series mechanics.

The central table is declared as a hypertable. Behind a single logical table, TimescaleDB manages automatic partitioning into time slices — chunks — cut here into seven-day intervals. A time-bounded query only touches the relevant chunks, which avoids scanning the entire history to return one week. At the close of the internship the hypertable held fifteen chunks for 103,940 measurements.

Fast access rests on a composite index designed for the dashboard's actual load:

The column order is not arbitrary: it matches the exact shape of the queries, which filter first on a station, then on a parameter, before sorting by descending time. The execution plan, checked with EXPLAIN ANALYZE, confirms the index is used and that no sequential scan occurs — including on compressed chunks, where the engine falls back to a vectorised columnar scan.

The result Native columnar compression, configured to segment by station and parameter and order by descending time, takes the history from 29 MB to 2.3 MB — a factor of 12.7, thirteen of the fifteen chunks compressed, without losing a single row. Combined with Docker log rotation and image build cache cleanup, the operation brought the VM's disk usage down to 17.4%, freeing close to 9.4 GB.

Because the TimescaleDB version in use allows writes on compressed chunks, ingestion and correction stay fully operational on that condensed history. At the current ingestion rate, the compressed database grows so slowly that the available capacity covers a horizon of several decades.

07

API and exports: removing every ambiguity

Data is exposed through a FastAPI backend: automatic parameter validation from type hints, OpenAPI documentation generated for free, and access to Python's scientific ecosystem for the export.

Every read route aggregates to the standard step using TimescaleDB's time_bucket function:

One refinement is worth calling out: the chart and the table never request all of a station's parameters, only the series actually on screen, through a server-side filter. That restriction cuts the transmitted payload by an order of magnitude. Time-bound normalisation is also centralised in a single function that rejects, with a structured 400, any range where the start date would come after the end date — mirroring the validation done in the interface.

The Excel export, and the timezone question

The users' request was precise: a genuine Excel file, usable in a spreadsheet, where each parameter occupies its own column. The function is built on pandas, whose pivot_table performs the shift from long format — one row per measurement — to wide format — one row per timestamp, one column per parameter — which openpyxl then renders as .xlsx.

Since timestamps are stored in universal time, the export converts them to the timezone selected on screen, then writes that timezone explicitly into the header of the time column. A scientist opening the file therefore reads Timestamp (Local time Europe/Paris, UTC+02:00) or Timestamp (UTC), with no ambiguity whatsoever. Parameter headers carry a readable label and its unit — Temperature (°C), Dissolved oxygen (mg/L) — rather than internal technical identifiers.

The final check was run in production against the real binary file: the same reading appeared at 14:02 in local time and 12:02 in universal time, the two-hour gap confirming the summer-time calculation was correct.

08

Interface: 60 frames per second over three months of data

The React / TypeScript frontend's challenge was not functional but performance-related. Displaying several months of measurements at a fifteen-minute step means asking the browser to draw tens of thousands of segments, the vast majority of which overlap to the point of being invisible. Rendering saturated the main thread and every interaction turned sluggish.

The answer is LTTB (Largest-Triangle-Three-Buckets). Its principle: keep not every other point mechanically, but the points that carry the visual information — those that form, with their neighbours, the largest triangles, meaning the inflections and the peaks. I capped rendering at 1,800 points, a threshold beyond which the eye sees no further detail but the processor pays dearly. The curve stays faithful, the scientifically meaningful extrema are preserved, and the DOM load collapses.

The detail that makes the difference How effective that reduction is depends entirely on where it is computed. The classic mistake is to recompute the downsampling on every render, including when the user is merely moving the mouse. So I isolated the computation in a useMemo whose dependencies include the data and the zoom window but deliberately exclude every variable tied to cursor movement — position, selection preview, tooltip state. Resampling therefore only fires when the data actually changes, never sixty times a second during a hover.

A two-dimensional rectangular zoom

With one drag, the user defines a rectangle that simultaneously narrows the time window on the x-axis and the value range on the y-axis. I gave up relying on the charting library's event metadata, unreliable depending on the plot type, in favour of reading the render area's geometry and the native mouse coordinates directly — which gives identical behaviour across every chart.

The vertical scale adjusts to the values actually present, between their minimum and maximum, without ever forcing the origin to zero. That point is crucial for seeing small variations around a high value, such as salinity in a marine environment.

Reading against the tides

The tide's influence on an estuary's salinity and turbidity is decisive: that correlation is precisely what oceanographers are after. A second chart, fed by the forecasts for the port of Bayonne / Boucau, shares a synchronisation identifier with the main chart: the hover cursor and the zoom window propagate instantly from one to the other.

09

Correction: set aside without ever erasing

This last building block answers the third tension: preserve trust in the data without ever altering it irreversibly. The principle is logical deletion. When an administrator sets aside a range of measurements — because it corresponds to maintenance or to obvious drift — no row is physically deleted. The measurement receives a quality flag that excludes it from every public view without destroying it; maintenance periods follow the same logic with their own flag.

Public-facing queries systematically filter on those flags, while administration routes return the full dataset for diagnosis. Reversibility takes shape in a dedicated tab that lists the complete history of hidden measurements: each row carries a restore button that, in one click, brings the data back into the charts and tables. Every action — deletion as well as restoration — is recorded in a correction log.

The raw archive stays intact at all times. Every correction decision remains recoverable, a guarantee without which a scientific instrument could not be credible.

Dynamic thresholds to make anomalies legible

An administrator can define, for each station-parameter pair, a lower and an upper bound beyond which a value counts as abnormal. Those thresholds are stored in the database and held in an in-memory cache with a thirty-second time to live, invalidated on every write, so that evaluation happens in real time at no extra query cost.

Every measurement sent to the frontend then carries an out-of-bounds indicator, used visually: a crimson marker on the curves, red highlighting in the tables, an explicit note in the tooltip. The anomaly becomes immediately legible, without the analyst having to mentally compare each value against a reference.

Everyday queries — the ones a scientist fires dozens of times per session — settle under the fifty-millisecond mark, the threshold below which a response feels immediate. Only pulling three months at full resolution reaches 117 ms, a comfortable figure for an operation that heavy, and one that still rides the index without a sequential scan. The ratio between the cost of that extreme query and that of the everyday ones is exactly the benefit of the architecture: the system does not degrade abruptly as load grows.

What I would do differently

The network currently has only two genuinely active stations: the pipeline's generic nature was verified, but not stress-tested at scale. The deployment procedure — copying files then rebuilding only the affected container — is still manual and would benefit from a continuous integration pipeline. And test coverage leans more on systematic acceptance testing in real conditions than on an exhaustive unit test suite: a pragmatic choice within an internship, but one with room to improve.

What the platform now makes possible

An administrator can declare a new station straight from the browser: entering the name, the feed code, the probe type and its sensors is enough to create the database entry, automatically associate the right parser, provision the receiving FTP subfolder and make the probe appear everywhere in the interface, with no recompilation at all. Adding an instrument, once a development task, becomes a configuration step.

Beyond that, the normalised corpus — clean and homogeneous — is fertile ground for more ambitious analysis: automatic anomaly detection, multi-parameter correlations, predictive modelling of certain quantities against the tides.
